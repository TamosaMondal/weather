# Weather Bookmark Dashboard

A logged-in dashboard where a user searches for a city, saves it as a
"bookmark," and sees its live temperature, weather description, and air
quality (AQI) — with rename, pin, refresh, and delete. Built with plain
**HTML + CSS + PHP** (no framework), a moderate amount of **vanilla
JavaScript** for UX (themes, menus, live alerts, SPA navigation), and
**Open-Meteo** + **Wikipedia** for all live data — **no API key required
for anything**.

No frameworks, no build step, no separate database server — just PHP files
you can run directly. SQLite is the only "database," and it's a single
auto-created file.

---

## 1. Tech Stack

| Layer        | Choice                                                             |
|--------------|---------------------------------------------------------------------|
| Backend      | PHP 8 (plain, procedural, no framework)                             |
| Database     | SQLite (single file, `database.sqlite`, auto-created on first run)  |
| Frontend     | HTML + CSS (`css/style.css`)                                        |
| JavaScript   | Vanilla JS — SPA router, themes, menus, sort/layout, live alerts, spinners, skeletons |
| Weather/AQI  | [Open-Meteo](https://open-meteo.com) forecast + air-quality APIs (no key) |
| Places       | Open-Meteo geocoding + [Wikipedia](https://www.wikipedia.org) geosearch (no key) |

Open-Meteo was chosen over OpenWeatherMap specifically because it needs **no
API key** — important on locked-down corporate machines where signing up
for/injecting a third-party key isn't practical (see the SSL note below).

SQLite was chosen instead of MySQL so the project runs with **zero database
setup** — PHP talks to it through PDO, and the file is created automatically
the first time the app runs.

## 3. How the pieces connect

**Every page starts the same way.** `login.php`, `register.php`,
`dashboard.php`, `profile.php`, `help.php`, `logout.php`, and every file in
`actions/` begin with:

```php
require_once 'includes/bootstrap.php';
```

`bootstrap.php` does three things, in order:
1. `session_start()` — so `$_SESSION` works everywhere.
2. Loads `config/config.php` (Open-Meteo endpoint URLs, DB path,
   `SSL_VERIFY_PEER`) and `config/db.php` (gives you the `getDB()` function).
3. Loads `includes/functions.php` (helper functions like `require_login()`,
   `fetch_weather()`, `geocode_city()`, `h()` for escaping, `redirect()`).

**Pages that render HTML** (`login.php`, `register.php`, `dashboard.php`,
`profile.php`, `help.php`) include `includes/header.php` before their
content and `includes/footer.php` after it, so the `<head>`, top navigation
bar, and closing tags/`<script>` stay identical everywhere.

**Pages in `actions/`** never output HTML. Most read `$_POST`, do one job
(insert / update / delete a row, or call the weather API), set a short
message in `$_SESSION['flash']`, and redirect back to `dashboard.php`, which
displays that message at the top of the page. `city_suggestions.php` and
`city_places.php` are the exception — they're called via `fetch()` from
`js/script.js` and return raw JSON, powering the autocomplete dropdown and
the "famous places" panel while the user is still typing.

### The SPA navigation model

`js/router.js` turns the multi-page app into a seamless single-page
experience:

- The `<header>`, `<footer>`, sky background, and loading overlay are
  rendered **once** on the initial page load and never re-rendered.
- Every subsequent navigation (link click or form submit) is intercepted by
  `router.js`, which `fetch()`es the target URL, parses the response with
  `DOMParser`, extracts only the `<main id="spa-main">` innerHTML, and swaps
  it into the existing `<main>` — the rest of the page stays frozen in place.
- The URL is updated with `history.pushState`; the browser's Back and Forward
  buttons work correctly via `popstate`.
- After each swap, `router.js` calls `window.WD.init()` (defined in
  `script.js`) to re-wire all event listeners and re-apply all preferences
  (theme, unit, layout, etc.) for the new content.
- `logout.php` is excluded from SPA interception so the session destroy and
  server-side redirect still work normally.
- A subtle `fade-in + slide-up` CSS animation on `main#spa-main` makes each
  content swap feel polished rather than an instant snap.

### The CRUD flow, file by file

| Action | Triggered from                     | Handled by                     | What happens |
|--------|-------------------------------------|---------------------------------|--------------|
| Create | Search form on `dashboard.php`      | `actions/add_city.php`          | Geocodes the name, fetches weather + AQI from Open-Meteo, `INSERT`s a row into `cities` |
| Read   | Loading `dashboard.php`             | `dashboard.php` itself          | `SELECT * FROM cities WHERE user_id = ? ORDER BY pinned DESC, updated_at DESC` |
| Update (alias) | "Rename" button + inline form | `actions/update_city.php`     | `UPDATE cities SET alias = ? WHERE id = ? AND user_id = ?` |
| Update (pin) | "Pin"/"Unpin" button           | `actions/pin_city.php`          | Flips the `pinned` flag; pinned cities always sort first |
| Update (weather) | "Refresh" button           | `actions/refresh_weather.php`   | Calls the weather/AQI fetch again and updates the row |
| Delete | "Delete" button                     | `actions/delete_city.php`       | `DELETE FROM cities WHERE id = ? AND user_id = ?` |

Every query that touches a row is scoped with `AND user_id = ?`, so one user
can never edit or delete another user's saved cities.

### Authentication flow

- `register.php` hashes the password with `password_hash()` and inserts a row
  into `users`, then logs the user in immediately (sets `$_SESSION['user_id']`).
- `login.php` looks up the username, verifies the password with
  `password_verify()`, and sets the same session variables.
- `includes/functions.php` has `require_login()`, which every protected page
  (`dashboard.php`, `profile.php`, and everything in `actions/` except the
  two AJAX endpoints) calls at the top. If there's no active session, it
  redirects to `login.php`.
- `logout.php` clears `$_SESSION` and destroys the session.

### The weather / AQI / places API calls

All external calls live in `includes/functions.php`, all pointed at
Open-Meteo (no key) and Wikipedia (no key):

- `geocode_city($city)` / `geocode_city_matches($city, $count)` — turn a
  free-text name into lat/lon (+ display name), the second returning several
  candidates for the autocomplete dropdown.
- `fetch_weather($city)` — geocodes, then fetches current weather +
  air-quality **concurrently** via `http_get_json_multi()` (not
  sequentially), and returns one clean associative array.
- `weather_code_to_info($code)` — maps Open-Meteo's WMO weather codes to a
  human description + emoji icon.
- `aqi_to_category($aqi)` — maps a raw AQI number to a category label
  (Good / Moderate / … / Hazardous), used both for the colored badge on each
  card and for the Notifications alert logic (see §4f).
- `famous_places_for_city()` / `wikipedia_landmarks_near($lat, $lon)` /
  `fetch_landmark_thumbnails_multi()` — power the "famous places" panel,
  falling back to a live Wikipedia geosearch for any location, not just a
  fixed list.

**Corporate proxy note:** `config/config.php` sets `SSL_VERIFY_PEER` to
`false` permanently for this build, because this copy runs behind an
SSL-inspecting corporate firewall (Zscaler/Netskope-style) that re-signs
HTTPS traffic with its own root CA, which PHP/cURL doesn't trust by default
— every Open-Meteo/Wikipedia call would otherwise fail with a cert error.

## 4. Feature history (what's been added, and how)

### a) Dark / Pink themes + the original black dark-mode

- Originally a single 🌙 toggle button; now driven by the **Settings ›
  Theme** menu (Light / Dark / Pink) described in §4c.
- The choice is saved in `localStorage` (`wd_theme`) and re-applied
  instantly on every page load via a tiny inline `<script>` in
  `includes/header.php` (runs before first paint, so there's no
  wrong-theme flash). Because the header is never re-rendered by the SPA
  router, the theme also never flashes on navigation.
- All theme styling lives in dedicated blocks in `css/style.css`
  (`html.dark-theme …` / `html.pink-theme …`), covering the header, footer,
  every card type (city/profile/auth/help/FAQ), inputs, links, and the menu.

### b) Skeleton loading + spinners

- **Skeleton:** `dashboard.php` renders a `.skeleton-grid` of placeholder
  cards immediately, alongside the real `#cityGrid` (hidden via
  `.content-loading`). Once the page finishes loading, `js/script.js`
  removes the skeleton and reveals the real grid.
- **Spinners:** every action button (Add city, Pin, Refresh, Rename/Save,
  Delete) gets an inline `.spinner` and an `.is-loading` state the moment
  its form is submitted. Handled generically in `js/script.js`
  (`addSpinnerOnSubmit()`), so any new form with a `<button type="submit">`
  picks it up automatically.

### c) Reusable Menu component — now powering 6 navbar menus

**`includes/menu.php`** is a generic, data-driven menu: `render_menu($items,
$options)` renders a `<ul>`/`<li>` tree from a plain PHP array, and any item
can have a `children` array nested as deep as needed. **`js/menu.js`**
handles click-to-open, click-away-to-close, and keyboard support
(Enter/Space, Arrow Down, Escape) for every `.menu` on the page automatically.

`includes/header.php` builds one item array per parent menu, then assembles
them (in this order) into `$mainMenuItems` (logged-in) / `$guestMenuItems`
(guest) and calls `render_menu()` once:

| # | Parent menu           | Children                                               | Depth |
|---|------------------------|--------------------------------------------------------|-------|
| 1 | **Dashboard** / Account | plain link (logged-in) / Login, Register (guest)       | 1–2   |
| 2 | **Help**                | FAQ, Contact, About → all real anchors on `help.php`    | 2     |
| 3 | **Display**             | Layout → Grid/List · Card Size → Compact/Comfortable/Large · Sort → Name/Pinned/Recently Updated | 3 |
| 4 | **Hi, {username}**/Account | Profile, Logout (logged-in) / Login, Register (guest) | 2     |
| 5 | **Settings**            | Theme → Light/Dark/Pink · Units → Celsius/Fahrenheit    | 3     |
| 6 | **Notifications**       | Weather Alerts → On/Off · Alert Threshold → All Cities/Severe Only | 3 |

Every leaf option (`Light`, `Grid`, `On`, etc.) is a real `<a>` with a
`data-*-option` attribute (e.g. `data-theme-option="dark"`); `js/script.js`
attaches one click handler per attribute type, so adding a 7th menu is just:
add an array in `header.php`, add a matching handler block in `script.js`.
Every menu shares one `css/style.css` block (search `Menu component`) plus a
`.menu-link[data-*-option].is-selected::after { content: '✓' }` rule that
shows a checkmark on whichever option is currently active.

To add another menu elsewhere in the app: build an `$items` array (see the
doc comment at the top of `includes/menu.php` for the exact shape) and call
`render_menu($items, ['id' => 'someId'])` — no JS/CSS wiring needed beyond
your own option handlers.

### d) Display menu — actually reshapes the dashboard

All three preferences persist in `localStorage` and are applied by
`js/script.js` directly to `#cityGrid` (the id on the real `.city-grid` in
`dashboard.php`):

- **Layout** — `grid` (default) or `list`; `list` adds a `.layout-list`
  class that reflows each `.city-card` into a horizontal row (CSS in
  `css/style.css`, search `Layout (Grid / List)`).
- **Card Size** — `compact` / `comfortable` (default) / `large`; adds a
  `.card-size-*` class to `#cityGrid` that resizes icon, padding, and
  temperature text.
- **Sort** — `name` (A–Z), `pinned` (default — pinned first), or `updated`
  (most-recently-updated first); re-orders the actual `.city-card` DOM nodes
  inside `#cityGrid` using `data-name` / `data-pinned` / `data-updated`
  attributes that `dashboard.php` now prints on each card.

### e) Help & Support page — FAQ accordion + sticky left nav (`help.php`)

The FAQ section is now a two-column layout:

- **Left column** — a sticky `.faq-nav` panel listing all question titles as
  links. It stays visible as you scroll down the right column. Clicking a
  link opens that accordion item and smooth-scrolls to it.
- **Right column** — a `.faq-list` of `.faq-item` accordion cards. Clicking
  a question's header expands its answer (and collapses any previously open
  item). A CSS chevron rotates to indicate open/closed state.
- **Scroll-spy** — an `IntersectionObserver` in `js/script.js`
  (`initFaq()`) watches which `.faq-item` is in the viewport and adds
  `.faq-nav-active` to the matching left-nav link, keeping the two columns
  in sync as the user scrolls.
- On screens narrower than 640 px the layout collapses to a single column
  and the nav becomes static (no longer sticky).
- The Contact and About sections below the FAQ remain as plain `.help-card`
  blocks, unchanged.
- All new elements (`faq-nav`, `faq-item`, `faq-question`, `faq-answer`,
  `faq-caret`, `faq-nav-active`) are fully themed for Dark and Pink modes in
  `css/style.css`.

### f) Notifications menu — live weather-alert banner

Also fully functional. When **Weather Alerts** is On (the default),
`js/script.js` (`computeAndRenderAlerts()`) scans every card in `#cityGrid`
on load and after every Display/Notifications change, using each card's
`data-temp-c` (always stored in Celsius, independent of the display unit)
and `data-aqi-category` attribute:

| Alert Threshold | Triggers on temperature                | Triggers on AQI category                             |
|------------------|------------------------------------------|--------------------------------------------------------|
| **All Cities**   | ≥ 35°C or ≤ 5°C                          | Unhealthy for Sensitive Groups, Unhealthy, Very Unhealthy, Hazardous |
| **Severe Only**  | ≥ 40°C or ≤ 0°C                          | Very Unhealthy, Hazardous                               |

Any matching city is listed in an amber `#weatherAlertsBanner` div at the
top of the "Your Saved Cities" section (see `.weather-alerts-banner` in
`css/style.css`); the banner hides itself automatically if alerts are Off or
nothing currently qualifies.

### g) SPA router — seamless page transitions (`js/router.js`)

The app now navigates without full page reloads:

- `js/router.js` uses **event delegation** on `document` to intercept every
  `<a>` click and `<form>` submit before the browser handles them.
- It `fetch()`es the target URL (GET for links, POST for forms), parses the
  full HTML response with `DOMParser`, and extracts only the
  `<main id="spa-main">` innerHTML — the part that actually changes between
  pages.
- That content is injected into the existing `<main>`, the URL is updated
  with `history.pushState`, and `window.WD.init()` is called to re-wire all
  event listeners and re-apply all `localStorage` preferences for the new
  content.
- The `<header>`, `<footer>`, sky background, and loading overlay are
  rendered **once** and never touched again — only the centre of the screen
  changes.
- The existing centered loading overlay (spinner) is reused as the
  between-page loading indicator.
- `logout.php` is excluded from interception so the server-side session
  destroy and redirect work normally.
- `js/script.js` was refactored to expose all its logic through
  `window.WD.init()`. `dataset` guards (`spinnerBound`, `confirmBound`,
  `faqBound`, etc.) prevent event listeners from stacking up across multiple
  `init()` calls on the same DOM nodes.

## 5. Database schema

Created and migrated automatically by `config/db.php` the first time the app
runs (older databases get the newer columns added via `ALTER TABLE`).

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    username TEXT UNIQUE NOT NULL,
    password TEXT NOT NULL,          -- hashed with password_hash()
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE cities (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,        -- which user saved this city
    city_name TEXT NOT NULL,         -- real city name returned by the API
    alias TEXT,                      -- user's custom nickname
    country TEXT,
    temperature REAL,
    weather_desc TEXT,
    weather_icon TEXT,
    latitude REAL,
    longitude REAL,
    aqi INTEGER,
    aqi_category TEXT,
    pinned INTEGER DEFAULT 0,        -- 1 = shown first on the dashboard
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY(user_id) REFERENCES users(id)
);
```

## 6. Security notes (kept intentionally simple, but not careless)

- Passwords are hashed with `password_hash()` / verified with
  `password_verify()` — never stored in plain text.
- All SQL uses **prepared statements** (PDO), so there's no SQL injection.
- All output printed back into HTML goes through the `h()` helper
  (`htmlspecialchars`), so there's no XSS from city names, aliases, etc.
- Every city query is scoped to the logged-in `user_id`.
- `SSL_VERIFY_PEER` is disabled — a deliberate, documented trade-off for
  this specific corporate-proxy environment (see §3), not a default you'd
  want on a normal deployment.

This is a learning/demo project, so things like CSRF tokens, rate limiting,
and email verification were left out on purpose to keep the code easy to
read — see `SETUP.md` if you want to extend it.

For setup instructions, see **SETUP.md**.
